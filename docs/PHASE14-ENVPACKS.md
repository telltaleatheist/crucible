# Phase 14 — Environments come from the release

**Owen, 2026-09-14:** *"we should use gh releases to download the environments we need to run
it, just like we do in bookforge. go ahead and set it up."*

BookForge already does this for its own runtime (a packed env on a GitHub Release, sha256
verified, split into <2 GiB parts, a version stamp that forces re-download). This phase gives
Crucible the same thing for EVERY environment it runs — the server's own interpreter and each
job type's env — so that installing a Crucible on a fresh machine downloads and unpacks, and
never builds. Building from recipes stays, as the DEVELOPER's explicit path and as the thing
that PRODUCES the packs.

## 0. What it deletes

- **The conda requirement.** `@crucible/bootstrap` today probes `~/anaconda3 | ~/miniconda3 |
  ~/miniforge3` for an env named `crucible` on Python 3.11 and refuses when absent — which is
  every fresh machine. Gone: the server pack carries its interpreter. `DEFAULT_CONDA_ROOTS`,
  `SERVER_ENV_NAME`, the `probeInterpreter` conda walk and the `no_conda`/`no_python` refusals
  are deleted, not kept as a second path.
- **`pip install <wheel>` on the host.** The server pack already has the wheel installed.
- **Minutes of pip per job type.** `crucible install tts` becomes a download and an unpack.
- **The user's own Python.** Nothing in Crucible depends on a distro's Python, its version, or
  its packages. A pack is self-contained.

## 1. What a pack is

A pack is a **relocatable, self-contained Python tree**: a standalone CPython build
(python-build-standalone, the interpreter `uv` ships — relocatable by construction, relative
rpaths, no absolute paths baked in) with the env's packages installed INTO it (not a venv
beside it — venvs carry the base interpreter's absolute path and do not survive a move).
Unpacked anywhere, `<dir>/bin/python` runs, `<dir>/bin/crucible` runs.

One pack per **(name, backend, crucible version)**:

| pack | name | what is inside |
|---|---|---|
| the server | `server` | CPython 3.11 + the crucible wheel and its deps; `bin/crucible` |
| one per job env | `llm`, `asr`, `align`, `rvc`, `tts-higgs-v3` | CPython + that recipe (`envs/<type>/<recipe>.txt`, unchanged) |

Backends: `cuda-linux` (built on Linux x86_64) and `mlx-darwin` (built on macOS arm64). The
build machine does not need a GPU — pip does not. `denoise` shares the `rvc` env and has no pack
(`cli.INSTALLER_FOR` already says so).

**Naming, exactly:** `crucible-env-<name>-<backend>-<version>.tar.zst`, split as needed into
`….tar.zst.part00`, `.part01`, … each < 1900 MiB. zstd, not gzip: an 8 GB torch env unpacks
in a fraction of the time, and `tar --zstd` is on every target (Ubuntu ≥ 20.04, macOS ≥ 10.15
via the tar the pack's own build ships — see 3.3).

## 2. The manifest: `envpacks.json`

One JSON asset per release, generated by the build, the single owner of what packs exist:

```json
{
  "schema": 1,
  "version": "0.6.0",
  "packs": [
    {
      "name": "llm", "backend": "cuda-linux",
      "python": "3.11.13",
      "bytes": 8123456789, "sha256": "…of the whole archive…",
      "parts": ["crucible-env-llm-cuda-linux-0.6.0.tar.zst.part00", "….part01", "….part02", "….part03", "….part04"],
      "recipe_sha256": "…sha256 of envs/llm/cuda-linux.txt at build time…",
      "unpacked_bytes": 9012345678
    }
  ]
}
```

- `sha256` and `bytes` describe the REASSEMBLED archive (BookForge's rule). Each part is fetched,
  appended, deleted; peak extra disk is one part.
- `recipe_sha256` is what ties a pack to the recipe it was built from: `crucible install`
  refuses `pack_recipe_drift` when the running server's recipe hash differs from the pack's —
  a pack built from an older recipe is not "close enough" (R3).
- `unpacked_bytes` is what the pre-flight disk check uses.
- A `(name, backend)` absent from the manifest is a named refusal `pack_not_published`, never a
  quiet build.

## 3. The three verbs

### 3.1 `crucible install <type>` — download, verify, unpack (the default)

For the running server's version and backend: read `envpacks.json` from the release
(`https://github.com/telltaleatheist/crucible/releases/download/v<version>/envpacks.json`),
find the pack, pre-flight disk (`unpacked_bytes` + one part), fetch parts into
`~/.crucible/downloads/` with resume, verify the whole sha256, unpack into
`~/.crucible/envs/<key>.partial/`, then atomic rename to `~/.crucible/envs/<key>/`, write the
stamp with the pack's sha256. A half-done unpack is `.partial` and is removed on the next run.
Progress: the same `progress {bytes_done, bytes_total, file}` events the pull task already
emits (3.3 of PHASE13), so the operator page draws it unchanged.

Refusals by name: `pack_not_published`, `pack_manifest_unreadable`, `pack_download_failed`,
`pack_sha_mismatch` (the archive is deleted), `pack_recipe_drift`, `pack_disk` (with the
numbers), `pack_unpack_failed`.

`--build` is the explicit developer path: the recipe, `python -m venv` as today. It is an
argument, not a fallback: nothing chooses it because a download failed.

### 3.2 `crucible envpack build <name>` — produce a pack (developer / CI)

On the backend it targets: fetch the pinned python-build-standalone release for the pack's
Python version (pinned in `crucible/envpack.py`, one place, with its sha256), unpack it,
`pip install -r <recipe>` into it, prune (`__pycache__`, tests, `.dist-info/RECORD` stays),
tar with zstd, split, sha256, and append the entry to a local `envpacks.json`. `--check`
verifies an existing pack matches its recipe hash. The server pack additionally
`pip install`s the wheel `python -m build` just produced.

A pack is SMOKE-TESTED before it is uploaded: unpack to a temp dir, run
`<dir>/bin/python -c "import <the env's engine module>"` (vllm / faster_whisper / …), and for
the server pack `<dir>/bin/crucible --version`. A pack that does not pass is not an asset.

### 3.3 `release.sh` + CI — build on the target OS, upload beside the four assets

`release.sh` keeps cutting the tag and the four existing assets. A new workflow
`envpacks.yml` runs ON THE TAG: a matrix of (pack × backend) — `ubuntu-latest` for
`cuda-linux`, `macos-14` (arm64) for `mlx-darwin` — each job builds ONE pack, smoke-tests it,
uploads its parts with `gh release upload --clobber`, and uploads its manifest fragment; a
final job merges the fragments into `envpacks.json` and uploads that LAST — so a release
whose manifest exists has every pack it names. A job that fails leaves the manifest without
that pack, which `install` refuses by name (`pack_not_published`) — never a half pack.

Runner disk is finite (~14 GB free on ubuntu-latest): one pack per job, prune the
python-build-standalone download after unpack, delete the unpacked tree after tarring. If a
pack cannot fit a hosted runner, the job says so and that pack is built on Owen's machines by
`crucible envpack build` and uploaded by hand — recorded here, not discovered at release time.

## 4. Bootstrap: install a server without conda

`install()`'s sequence becomes:

```
host-facts       WSL2 distro / Apple silicon, the card, disk (unchanged probes; conda walk DELETED)
server-pack      download + verify + unpack crucible-env-server-<backend>-<ver> into
                 ~/.crucible/server/            (the host names the RELEASE, never a path)
init             <server>/bin/crucible init --token …   (skipped when a config exists)
install-<type>   <server>/bin/crucible install <type>   (3.1 — downloads the job pack)
service-install  <server>/bin/crucible service install  (ExecStart points at the pack's bin)
linger           win32, as root, as built in 0.6.0
capability-write
```

`readLocalConfig()` unchanged. `ensureRunning()` unchanged. The wheel option and the conda
options are deleted from `InstallOptions`; `release` (a version) replaces them. The bootstrap
package's version already equals the server's, so "which release" is never a question.

Windows→WSL: the download runs INSIDE the guest (`wsl.exe --exec <server>/bin/crucible …` after
the server pack exists; the server pack itself is fetched by the guest's `curl` — which every
distro has — into the guest filesystem, never through `/mnt/c`, which is slow and breaks
permissions).

## 4a. Crucible installs on its own, and every app coordinates with whatever is there

**Owen, 2026-09-14:** *"we should be able to install crucible independently of bookforge, and
if its present, bookforge should coordinate with the installed crucible to make sure it has
what it needs to run all of its features. same with foundry."*

Two consequences, both built in this phase:

**A standalone installer, shipped as release assets.** `install.sh` (Linux/WSL and macOS) and
`install.ps1` (Windows: ensures WSL2 + a distro, then runs `install.sh` inside it) do exactly
what bootstrap's `install()` does — the same sequence, the same server pack, the same
`crucible init` / `service install` / linger — with NO job types and NO weights: a bare
Crucible that serves nothing until an app or the page asks. The scripts are generated from
the same step list bootstrap uses (one owner: `sdk/bootstrap/src/install.ts`'s sequence is
what the script generator reads), so an app-driven install and a hand install cannot differ.
A person types one line:

```
curl -fsSL https://github.com/telltaleatheist/crucible/releases/latest/download/install.sh | sh
```

and the last thing it prints is the pairing line (`crucible token --url`). On Windows, the
`.ps1` does the WSL minute (admin prompt for `wsl --install` if needed, reboot notice, resume)
and then the same.

**Every app coordinates on connect, not only on install — ASK, THEN ACT.** When an app finds
a Crucible — `local` on this machine, or a remote it was given — it READS `GET /v1/catalog`
(cheap, read-only, no lane) and compares its module against it. Nothing missing is a read
and nothing else: no task, no `task_busy` between two apps arriving at once, no
`server_busy` naming the app's own lease because its own book is running (Foundry's catch,
2026-09-14 — a task whose whole content would be `skipped` events must not be posted on a
server that runs one task at a time). Only when something IS missing is the module posted
(`POST /v1/tasks {type: module}`), and the task's events are drawn in a person's words
("Preparing the narration engine… downloading deathstalker 8.5 GB…"). A person never sees
the word module.

**No consent step — Owen, 2026-09-14: *"lets make it as simple as possible."*** Coordination is
automatic on EVERY server the app is connected to, local or remote, with nothing to press:
the person sees the progress sentence, never a question. Stated once so it is a choice and
not an accident: opening an app on a laptop connected to the Mac downloads onto the Mac
whatever that app needs that is not there yet. (Foundry's proposal of a one-press consent
on a remote registered in an earlier session was heard and overruled for simplicity;
disabling a server in Settings is the way to say "not that one".)

A module task refused `server_busy` (a lease, a job) is retried when the card settles, with
the holder named in the meantime. Foundry does the same with its own module. Two apps on
one machine = the union of two modules on one server, as PHASE5-APPS.md §6.0 always said.

This is what makes the split simpler than what it replaced: Crucible is a service you can
put on a machine by itself; an app that arrives later asks it for what the app needs; the
person never mediates between them.

## 5. What stays exactly as it is

The recipes (`envs/<type>/<backend>.txt`) — they are the pack's source of truth and the
`--build` path. The weights (HuggingFace, pulled by tasks). The service. The lease. The page.
`crucible doctor`, which now also reports each env's pack sha beside its recipe hash.

## 4b. A Crucible-owned WSL distro — IN SCOPE (Owen, 2026-09-14: "yes, lets do it. make it idiot proof")

On Windows, bootstrap and `install.ps1` do not use the person's Ubuntu. They `wsl --import
crucible <rootfs> <dir>` from a rootfs asset on the same release
(`crucible-rootfs-<version>.tar.zst`: a minimal Ubuntu 24.04 base image with `[boot]
systemd=true` and `[user] default=crucible` already in `/etc/wsl.conf`, the `crucible` user
created, no password, `curl`/`tar`/`zstd` present, nothing else). Consequences, each the
reason for it:

- **No first-run prompt.** `wsl --install -d Ubuntu` launches an interactive username/password
  dialog an app cannot answer; `--import` asks nothing.
- **No collision.** A person's own distro (and Owen's, with everything in it) is never touched;
  `local` on Owen's PC keeps reading his Ubuntu because his config is there. A machine with
  BOTH is refused by name (`two_local_crucibles`) rather than guessed between.
- **systemd is a fact, not a probe.** The image ships with it on; the "older install without
  systemd" repair (4c) is for people who chose their own distro by hand.
- **Idempotent.** A `crucible` distro already present is used, never re-imported; a partial
  import (no `/etc/wsl.conf` marker) is unregistered and redone.
- **The GPU is the host's driver.** WSL exposes the Windows NVIDIA driver into every distro;
  nothing to install in the guest. `no_nvidia_driver` names the Windows download.

The distro's name is `crucible`, its files live under `%LOCALAPPDATA%\Crucible\wsl\`, and
`crucible service uninstall --distro` removes it entirely — a person can delete the whole
thing with one command and their own WSL is exactly as it was.

## 4c. Every WSL state, detected and answered by name (the idiot-proof table)

| state | detected by | answer |
|---|---|---|
| no `wsl.exe` / WSL feature off | `wsl.exe --status` missing or errors | `Enable WSL` button: `wsl --install --no-distribution` under UAC (`Start-Process -Verb RunAs`); "restart, then open the app again"; resume at the next step |
| virtualization disabled in firmware | `wsl --install` / `--status` error text (HCS_E_HYPERV_NOT_INSTALLED, `0x80370102`) | cannot be fixed by software: the two-line firmware instruction (enable VT-x / SVM), then Enable WSL again |
| WSL1 only | `wsl --status` default version 1 | `wsl --set-default-version 2` (ours to run), then import |
| WSL present, no `crucible` distro | `wsl -l -v` | import the rootfs (4b) — download with progress |
| `crucible` distro present, not systemd | `/etc/wsl.conf` inside it | ours: write it as root, `wsl --terminate crucible` (only that distro — never `--shutdown`) |
| a hand-chosen distro without systemd | same probe | say so and ask before writing `wsl.conf` and terminating THEIR distro |
| no NVIDIA driver (guest has no `/dev/dxg` / `nvidia-smi`) | the existing probe | the driver download link; re-check button |
| no network in the guest (VPN/proxy) | the rootfs / pack download fails with a network error | named refusal with the URL that failed; nothing else to do but say so |
| not enough disk | pre-flight against `unpacked_bytes` + one part + rootfs | the number, before anything is downloaded |
| `wsl -u root` refused (a hardened distro) | exit code on the linger step | the one remaining hand-over: the exact `loginctl` line |

`install.ps1` and bootstrap share this table (one owner: the table is data in
`sdk/bootstrap/src/wsl-states.ts`, and the script generator emits it).

## 6. Not in this phase, written so it is not forgotten

- **Delta updates** between versions. A new version is a new pack; the old env dir is removed
  after the new one is stamped.
- **A pack for Windows.** Windows is never a backend.
